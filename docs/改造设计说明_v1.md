# 改造设计说明 v1

## 1. 目标

- 统一抓取执行入口与状态机。
- 消除全局配置污染。
- 统一错误协议，提升可观测性。

## 2. 任务状态机

状态流转：

`queued -> running -> success|failed`

字段说明：

- `task_id`：外部查询主键。
- `trigger_source`：`manual|schedule|feishu`。
- `requested_keyword_ids`：请求传入范围。
- `resolved_keyword_ids`：实际执行范围。
- `scrape_headless`：本任务运行模式覆盖。
- `error_code/error_message`：失败原因。
- `result_summary`：任务摘要 JSON。

## 3. 执行模型

1. `POST /api/scrape/trigger` 仅负责创建 `queued` 任务。
2. 统一 worker 串行消费队列，保证单实例互斥执行。
3. 调度器 cron 只入队，不直接执行抓取。
4. 飞书命令触发也走同一入队路径。

## 4. 参数隔离策略

- `scrape_headless`、`keyword_ids` 不写 `AppConfig`。
- 任务执行时通过运行时 override 传入 scraper。
- 任务 `finally` 阶段清理 override，防止串任务污染。

## 5. 错误协议

统一错误结构：

```json
{
  "code": "AUTH_INVALID",
  "message": "Invalid API key",
  "hint": "请检查 API Key 是否正确，并确认前端已同步最新配置。",
  "request_id": "a1b2c3..."
}
```

## 6. 接口变更

- `POST /api/scrape/trigger`
  - 入参：`keyword_ids[]`、`scrape_headless`
  - 出参：`task_id`、`queued_at`、`position`
- 新增 `GET /api/tasks`
- 新增 `GET /api/tasks/{task_id}`

## 7. 前端收敛策略

- 唯一控制台实现：`backend/static/dashboard.html`
- `frontend` 保留为 API 基址壳层，统一跳转到 `/dashboard`
